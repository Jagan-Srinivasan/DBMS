🎓 Database Normalization Journey

From 1NF to 5NF - Complete Demonstration

1NF First Normal Form

Rule: Eliminate repeating groups and ensure atomic values.

What we did: Ensured each column contains only atomic (indivisible) values. No arrays or multi-valued attributes.

❌ Before (Unnormalized):
Employee: John, Dept: HR,Finance, Salary: 50000, Hours: 160

✅ After 1NF:
Employee: John, Dept: HR, Salary: 50000, Hours: 160
Employee: John, Dept: Finance, Salary: 50000, Hours: 160
Each row now contains atomic values only

4NF Fourth Normal Form

Rule: Eliminate multi-valued dependencies (independent multi-valued facts about an entity).

What we did: Created separate tables for employee skills and certifications because they are independent multi-valued attributes.

Problem:
An employee can have multiple skills AND multiple certifications independently.
Storing them together creates redundancy: If John has 3 skills and 2 certs, we'd need 6 rows!

Solution (4NF):
skill: skill_id (PK), skill_name
employee_skill: emp_id (FK), skill_id (FK)
certification: cert_id (PK), cert_name
employee_certification: emp_id (FK), cert_id (FK)

Example:
Employee Skills: emp_id=1, skill="Python" emp_id=1, skill="JavaScript" Employee Certifications: emp_id=1, cert="AWS Certified" emp_id=1, cert="PMP"
✅ Skills and certifications are independent - no multi-valued dependencies

5NF Fifth Normal Form (PJNF - Project-Join Normal Form)

Rule: Eliminate join dependencies by decomposing into binary projections that can losslessly reconstruct the original data.

What we did: Decomposed the Consultant-Skill-Project triple into three binary relationships.

Problem (Before 5NF):
Storing (Consultant, Skill, Project) in one table creates a join dependency.
Business rule: A consultant can work on a project only if they have a skill required by that project.

Solution (5NF Decomposition):
consultant: consultant_id (PK), consultant_name
consultant_skill: consultant_id (FK), skill_id (FK)
skill_project: skill_id (FK), project_id (FK)
consultant_project: consultant_id (FK), project_id (FK)

Binary Projections: 1. Consultant ↔ Skill (consultant_skill) 2. Skill ↔ Project (skill_project) 3. Consultant ↔ Project (consultant_project) Lossless Join Reconstruction: SELECT c.consultant_name, s.skill_name, p.project_name FROM consultant c JOIN consultant_skill cs ON c.consultant_id = cs.consultant_id JOIN skill s ON cs.skill_id = s.skill_id JOIN skill_project sp ON s.skill_id = sp.skill_id JOIN project p ON sp.project_id = p.project_id JOIN consultant_project cp ON c.consultant_id = cp.consultant_id AND p.project_id = cp.project_id Example Data: • Alice has Python skill • Python is needed for Website Redesign project • Alice works on Website Redesign → Reconstructed: (Alice, Python, Website Redesign)
✅ The original triple is perfectly reconstructed from three binary tables - true 5NF!
🎯 Benefits of Full Normalization (1NF → 5NF)
  • Zero redundancy - Each fact stored exactly once
  • Data integrity - Foreign keys enforce referential integrity
  • Update anomaly prevention - No inconsistencies during updates
  • Scalability - Easy to add new attributes without restructuring
  • Flexibility - Independent facts can evolve separately
